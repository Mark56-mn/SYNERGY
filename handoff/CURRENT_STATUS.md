## Security posture
Authentication is resolved server-side from the request; no route or service trusts a browser-supplied user ID. Ownership, role and cross-user isolation checks are deny-by-default and covered by tests using clearly labelled test doubles. **Identity verification is implemented.** The implementation agent reports the real project returned 200 for `/auth/v1/settings`, rejected a forged token with 403, and the protected route returned 401; the running app reportedly detected configuration. This review verified the GitHub handoff, not those live network calls. A successful real-user token has not been exercised end-to-end (B-7b). `SupabaseSessionSource` now verifies bearer tokens through Supabase Auth's own `/auth/v1/user` endpoint (signature, issuer, audience, expiry and revocation are the provider's judgement), fails closed to `null`, and rejects non-UUID ids. It is configuration-gated, so without Auth credentials every protected route still denies. The 12 new tests use a stubbed HTTP transport; they prove local boundary behavior, not live provider integration. No test claims production-grade security. Cookie sessions, CSRF same-origin checks, sign-in/sign-up and logout were implemented by TASK-006B-auth-UI (HttpOnly cookies, edge refresh, logout with provider revoke); they live-verify via negative paths, with the positive path now owner-confirmed on the Preview. TASK-007 adds profile authorization: the acting identity comes only from the verified session, private profiles are answered as not found, public responses use an explicit allowlist, and cross-member denial, tampered bodies, CSRF, rate limiting and DTO shape are covered by tests with labelled doubles. Real persistence is proved separately against the isolated Neon branch (12 live checks), never by mocks.
